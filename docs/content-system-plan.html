Funnel-Stage Pre-System

The single biggest insight: generic content frameworks fail because they treat every post as the same job. A TOFU post that converts to a follow has different anatomy than a BOFU post that converts to a DM. This pre-system makes Michelle (or any client) tell us where the bottleneck is, then biases the entire pipeline toward fixing it.

1. The diagnostic wizard

Six questions, takes < 5 minutes (Q1-Q5 required, Q6 optional advanced setting). Lives in the client view of the dashboard. Re-takeable any time (e.g. after a quarter).

Q1 — What's your primary offer right now?
  • Free download / lead magnet → biases TOFU + email capture MOFU
  • Free discovery call / strategy session → biases MOFU + objection-handling BOFU
  • Paid program $1K–$10K (coaching / DWY) → biases MOFU + BOFU
  • High-ticket 1:1 $10K+ → biases BOFU + proof-heavy MOFU
  • Course / membership → biases TOFU broad + MOFU education
Q2 — Where do you feel your funnel is leaking the most?
  • Not enough people see me → TOFU bottleneck (reach problem)
  • People see but don't follow / engage → TOFU→MOFU transition
  • People engage but don't DM / book calls → MOFU→BOFU transition
  • They book calls but don't buy → out of scope for content (sales problem)
Q3 — Of the people who follow you, what % would say "I know exactly what Michelle does and who she helps"?
  • < 20% → market is unaware → TOFU + MOFU heavy
  • 20–50% → mid-positioned → MOFU heavy
  • 50–80% → known → BOFU + objection-handling heavy
  • 80%+ → already converted minds → BOFU + offer-stack content
Q4 — What's your specific 90-day outcome?

Free text + structured tags: followers, email subs, DMs, booked calls, revenue. This sets the winner-metric weighting for stage 06.

Q5 — What kind of content makes you cringe to make?

Constraint capture. Output appends to _config/constraints.md. e.g. "no point-to-camera B-roll", "no 'POV: you're a coach' hooks".

Q6 — Pillar comfort (optional advanced setting; Iman's dimension)

Skippable. If skipped, defaults apply. Four pillars: Educate · Sell · Story · Inspire. Iman's default for booked-calls is 40/30/20/10. "Sell has to be higher than most people are comfortable with." Wizard shows the default and lets the client adjust if specific pillars feel forced. Output: pillar_weights in funnel-goal.json.

3. How this biases each pipeline stage

Stage What changes per funnel-goal
01_ideateIdeas generated in the split ratio (e.g. 3 TOFU / 5 MOFU / 2 BOFU). Each idea tagged with stage. Source weighting shifts by stage: TOFU pulls more from outlier swipe + winners. MOFU pulls from offer angles + buyer-profile + sales-call objections (where the buyer was 80% sold but hesitated). BOFU pulls heavily from sales-call objections + buyer-profile — these are the moments a real buyer voiced their last block. One sales-call objection often spawns 2-3 distinct posts (objection raw, the reframe, the case study that resolves it).
02_scriptHook template + body structure + CTA differ by stage. TOFU = curiosity hook + broad pain + soft follow CTA. MOFU = specific problem + new mechanism tease + DM-keyword CTA. BOFU = proof / case / objection + direct call-booking CTA.
03_produceCaption length + hashtag set + cover image style adapt. TOFU caption is shorter, more curiosity; BOFU caption is longer, more proof-stacked. CTA copy mirrors script stage.
06_learnWinner metric uses per-stage weights from funnel-goal.json. A TOFU post is judged by hook rate × follow rate; a BOFU post by DM keyword hits + call bookings. Apples-to-apples is forbidden.

4. Hook rate × hold rate winner metric (mechanics)

From IG Insights per post (manual screenshot entry until API access is granted — see Dependency Log):

  • Hook rate = (3-second views / total impressions). Measures whether the opening earns attention.
  • Hold rate = (avg watch time / video length). Measures whether the rest of the video keeps it.
  • Stage-conditional bonus: add follow rate (TOFU), save rate (MOFU), profile visit rate + DM hits (BOFU).

Winner threshold = composite score > 3× the client's rolling 4-week average for the same funnel stage. This auto-fires Stage 06 decomposition.

The weekly scheduler — how it solves the constraint

The Six Stages

Each stage has a per-stage CONTEXT.md with the same five-field schema. Stages read only from the previous stage's output/ plus _config/. They never reach back to raw sources. The folder shape enforces the contract.

Stage 01 — Ideate (merge 3 sources)

Inputs: niche outlier pool + per-client overrides + client's weekly raw material (voice memos, notes) + _config/offer.md + _config/buyer-profile.md.

Process: AI generates 10–15 ideas. Each idea logs which of the 3 sources it came from (so we can tune source weighting later). Each idea tagged with its job-to-be-done (awareness, consideration, decision) and the implied hook spine.

Output: 01_ideate/output/<year-week>_ideas.md — a markdown table you can scan in 90 seconds.

Done-looks-like: Jerel ticks 3 ideas to move into scripting for this week. Untouched ideas roll forward.

Stage 02 — Script (voice-locked)

Inputs: the approved idea + all of _config/ + the hook bank.

Process: draft → voice-and-tone pass → format-patterns pass → constraints pass (kill the forbidden words). Output passes a forced "would this person actually say this?" check.

Output: 02_script/output/<post-id>_script.md with hook · body · CTA · b-roll cues if video.

Done-looks-like: Jerel reads the script in < 60 seconds, says yes or rewrites the hook. Approval bumps it to stage 3.

Stage 03 — Produce (assemble the pack)

Inputs: the approved script.

Process: generate caption (IG-spec), cover/thumbnail brief, post metadata (platforms, scheduled slot, hashtags), publish instructions for the client. If a video, queue the production prompts (Seedance / UGC pipeline).

Output: 03_produce/output/<post-id>/ folder with everything needed to publish.

Done-looks-like: the folder mirrors to Drive / here.now. Client receives a link.

Stage 04 — Approve (the gate)

Process: approval gate fires 3x per client per week. Web dashboard button (Phase 4+) or shared Google Doc check-off (Phases 1-3). Approval writes an immutable log entry. Rejection writes the reason — feeds the corrections loop.

Output: 04_approve/log.jsonl append-only.

Done-looks-like: nothing reaches publish without a logged approval.

Stage 05 — Publish (Drive / here.now handoff)

Process: the produce-folder is mirrored to a per-client Drive folder (or here.now Drive). Client gets a link with caption + asset + scheduled slot. They publish.

Output: 05_publish/manifest.md updated; drive_links.json updated.

Done-looks-like: the post is live; the Google Sheet row for that post flips to PUBLISHED.

Stage 06 — Learn (Brendan-style decomposition)

MVP analytics surface = manual screenshot entry into a Google Sheet (per Decision Register). Channel mix is IG + LinkedIn, not TikTok. No automated cron pulls until IG Insights API access is granted (Phase 6 dependency); LinkedIn has no public organic-personal Marketing API, so it stays manual indefinitely.

Voice Profile — the load-bearing piece

The whole system collapses if voice is wrong. We split it into three files (Jake's pattern) instead of a single mega brand-voice doc — each file answers one question:

_config/voice-and-tone.md

How do they sound?

Energy level, formality, default emotion, pace, register. Reference handles and exemplar posts. The qualitative layer.

_config/format-patterns.md

What shapes do they use?

Average sentence length. Typical hooks. Common transitions. Catchphrases. CTA structures. The mechanical layer.

_config/constraints.md

What must they never do?

Forbidden words. Avoided topics. Anti-patterns. The fence layer — a slop check before output ever leaves the script stage.

Capture method: scrape their existing socials (IG/LinkedIn — Michelle's channel mix; podcast if it exists) to draft v1 of all three files automatically. Then a targeted 30-min interview fills the gaps the scrape couldn't reach. Total setup: ~90 min/client. Reusable forever.

Agentic Voice Rules — stolen from Chase AI

Extracted verbatim from on-screen prompts and skill outputs in the pfPi04pIfaw frames. This is the voice our skills write in — not the voice the client posts in. Two different layers. (Client voice lives in _config/voice-and-tone.md; agentic voice lives in our skill output templates.)

  1. Arrow syntax over prose. Folders, skills, and CLIs are described with →, not "is". /raw → staging area · Shopify CLI → e-comm · CLAUDE.md → instructions. The arrow is the load-bearing element.
  2. Kebab-case-lowercase skill names. Always verb-noun or noun-noun. yt-pipeline · deep-research · content-cascade · vault-cleanup. Never VaultCleanup or VaultCleanupSkill.
  3. Bucket-and-count output format. Skill outputs lead with bold dated headers, then categorized bullets with counts up front. Numbers first, prose never. No "I've completed..." preambles.
  4. Confident operator hedges. Mid-execution notes read like a contractor's Post-it: "should verify… already moved. Safe: wiki-links resolve by filename, nothing breaks." One-line self-justification, not an apology.
  5. Domain-as-noun, skill-as-verb. System framing uses 5 nouns: MEMORY · PRODUCTIVITY · RESEARCH · CONTENT · CUSTOM. Inside each domain, skills are imperative actions (triage, send, draft). The two registers never mix.
