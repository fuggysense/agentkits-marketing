Blind spots only the peer-review caught

These NONE of the 5 advisors named — they only surfaced when reviewers compared takes:

  1. No unit economics anywhere. Nobody priced a single end-to-end run. Wrong default engine could 5x per-video cost silently. Architecture decisions without unit economics are taste arguments in system-design costume.
  2. Ground-truth signal is upstream of the ledger. "What makes a video good?" must be answered before the ledger schema is designed. Candidates: Jerel approval, render quality, Meta CTR/CPA (lagging, needs instrumentation), or operator taste verdict.
  3. Existing learnings infra collides with the new ledger. Per-skill corrections.md, learnings/session-state.md, global autoresearch already exist. Adding parallel video-ledger.json = two competing memories that drift apart.
  4. Live campaign protection. Skills are wired into routing-table.md, skill-graph.json. Nobody costed breakage to in-flight client deliverables mid-merge.
  5. Operator taste-authority rule. When ledger says "worked" but Jerel's gut says no — who wins? 80/20 HITL should govern ledger writes, not just approvals.
  6. Failure-mode catalog missing. Where does the pipeline currently break? Prompt drift, identity-lock failures, audio sync, revision loops? Ledger needs a failure-mode field per gen, not just good/bad.

First Principles"You're asking the wrong question. Build the spine first." Confidence 8/10
The frame is wrong. "Consolidate 12 skills into N" is an org-chart problem dressed up as architecture. It optimizes for Jerel's mental load when picking a skill, not for the machine getting better at making video.

Strip everything. The job-to-be-done: turn a marketing intent into a finished video that performs, and let every finished video make the next one cheaper, faster, and better.

Three primitives fall out:
  1. A brief (intent + constraints + DP profile + client context)
  2. A generator (whatever model/pipeline produces the asset)
  3. A ledger (what was made, what worked, what to copy/avoid)
Skills are interchangeable hands. The ledger is the spine. Right now Jerel has 12 hands and no spine — that's why it feels broken.

Minimum machine: brief.json (input contract) → router (picks generator by content-type, not by skill name) → video-ledger.json (output + scoring + learnings). Everything else becomes swappable executor behind that contract.

Consolidation is downstream of contract design. Build the contract first, and the skill mergers become obvious (and mostly unnecessary).

Re D: ledger isn't theater if it's the input to the next brief. MVP = three fields — what_we_tried, what_worked, dp_overrides_that_stuck — auto-prepended to the next brief in the same project.
